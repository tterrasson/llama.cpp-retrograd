# The Retrograd fork of llama.cpp

This branch (`retrograd/main` on `tterrasson/llama.cpp-retrograd`) carries the
changes Retrograd needs to *train* a model with llama.cpp: backward passes for
ops that only had a forward, the CPU, Metal, Vulkan and CUDA backends brought
up to the same contract, memory-efficient training machinery, and the RIR
generated-kernel integration.

It is a linear patch series on top of `upstream/master`: rebased, never merged.
Everything below exists so that the series stays readable, rebasable, and
partly proposable upstream.

## The series

```sh
git log --oneline upstream/master..HEAD  # one commit per patch family
git diff upstream/master...HEAD          # the whole delta
```

Each commit is `retro(<family>): <what>`, and each family is exactly one
commit. `<family>` is a key of the `[upstream_status]` section of
`crates/retrograd-ffi/runtime/llama.cpp.lock` in the Retrograd repository,
which records whether the family belongs upstream and why. The history and the
lockfile agree: a family in one and not the other is a bookkeeping bug.

The order is by dependency and by how likely a family is to leave:

1. `fork_docs`, `fork_footprint` — this file, `AGENTS.md`, and the fork-owned
   files the later families fill in;
2. fixes and backward passes in core ggml — small, self-contained, the most
   proposable;
3. backend implementations and new ops;
4. the optimizer and the training loop in `ggml-opt` and `llama-context`;
5. RIR — Retrograd-specific, the largest and the most often regenerated, last
   so that a regeneration only rewrites the top of the series.

A change to an existing family is a fixup of that family's commit. Between two
syncs it stays a separate commit, so publishing remains a fast-forward; the next
sync folds it in, and the series is back to one commit per family:

```sh
git commit --fixup=<family commit>            # day to day
git rebase --autosquash upstream/master       # at the next sync
```

A new family is a new commit, placed after what it depends on, plus its entry
in the lockfile. `scripts/check-llama-cpp-integration.sh` in Retrograd checks
that the series and the lockfile agree.

## Invariants

These are what keep a rebase onto a moving upstream cheap. Breaking one is
always possible, but it should be a decision, not an accident.

1. **Never delete an upstream file.** A deleted file that upstream keeps
   editing is a delete/modify conflict on every sync. GitHub Actions is turned
   off in the fork's repository settings rather than by deleting `.github/`.
   `AGENTS.md` is fork-owned on purpose: it is a *modification*, and on a
   conflict the fork's version wins.

2. **Additive code goes in a fork-owned file.** A new kernel, a new helper, a
   new translation unit — anything that is purely an addition — belongs in a
   file upstream has never heard of, reached from upstream's dispatcher by one
   line. The existing homes:

   | Backend | Fork-owned file | What goes in it |
   |---|---|---|
   | CPU | `ggml/src/ggml-cpu/retro-ops.cpp` | compute kernels the fork adds |
   | CPU | `ggml/src/ggml-cpu/retro-ops.h` | the few symbols `ops.cpp` calls back into |
   | Metal | `ggml/src/ggml-metal/kernels/retro.metal` | hand-written Metal kernels |
   | Metal | `ggml/src/ggml-metal/kernels/rir.metal` | generated RIR kernels |
   | Vulkan | `ggml/src/ggml-vulkan/ggml-vulkan-rir.cpp` | RIR SPIR-V blob lookup |
   | Vulkan | `vulkan-shaders/rir_*.comp` | generated RIR shaders |
   | CUDA | `ggml/src/ggml-cuda/{flash-attn-back,ssm-back,fused-sparse-ce,gated-delta-net-back,conv_rs_gather,opt-step-gefen}.cu` | training kernels |
   | CUDA | `ggml/src/ggml-cuda/rir/` | generated RIR kernels and their launchers |
   | shared | `ggml/src/ggml-retro-quant.h` | the dequant type table (generated by `rir-gen`) |
   | shared | `ggml/src/ggml-rir/` | the RIR registry, contract and dispatch |

   The two `.metal` files are per-op kernel libraries, one compiled Metal
   library each. Each one has to be listed **twice**: in
   `METALLIB_KERNEL_SOURCES` (`ggml-metal/CMakeLists.txt`), which compiles and
   embeds it, and in `GGML_METAL_LIBS` (`ggml-metal-device.m`), which is what
   the runtime searches. A file present in the first list only is compiled,
   embedded, and never found — `ggml_metal_library_compile_pipeline` reports
   `kernel not found in any metal library` and the caller dereferences a null
   pipeline.

3. **Rewrites of upstream functions stay in place.** Where the fork changes how
   an existing function behaves — `ggml_compute_forward_gated_delta_net`,
   `ggml_compute_forward_flash_attn_back_f32` — there is no seam to cut along,
   and moving the code would fork the function under another name. Those stay
   in upstream's file and show up as conflicts on rebase. That is correct:
   they *are* changes to upstream code.

4. **Every hunk in an upstream file says why.** The convention is a
   `// retro delta:` comment. It is what tells the next rebase whether a
   conflict should be resolved toward upstream or toward the fork.

5. **A new `GGML_OP` is expensive and that is nobody's fault.** Registering one
   means touching `ggml.h`, `ggml.c`, `ggml-alloc.c` and every backend's
   `supports_op` and compute switch. There is no way to make that additive.
   Weigh it before adding an op.

6. **Generated files are never edited here.** The RIR registry, kernels and
   shaders, `rir_kernel_params.h`, the CUDA launchers and `ggml-retro-quant.h`
   are copies of `rir-gen` output, compared byte for byte by
   `crates/rir-gen/tests/fork.rs` in Retrograd. Change the generator, then run
   `cargo run -p rir-gen --example sync-fork` there.

## Where the fork touches upstream files

The point of the table is that it should shrink. Regenerate it with:

```sh
for f in $(git diff --name-only --diff-filter=M upstream/master...HEAD); do
  printf '%3d  %s\n' "$(git diff -U0 upstream/master...HEAD -- "$f" | grep -c '^@@')" "$f"
done | sort -rn
```

The heavy ones, and why:

| Hunks | File | Why it is hard to shrink |
|---:|---|---|
| 75 | `ggml-vulkan/ggml-vulkan.cpp` | pipelines, `supports_op` and every op's encoder live in this one unit; the RIR chain is already one function (`ggml_vk_rir_try`), the rest is per-op registration |
| 57 | `ggml/src/ggml-opt.cpp` | the optimizer control surface: clipping, state access, scratch reuse, slot descriptors, master weights |
| 56 | `src/llama-context.cpp` | the training loop itself — packed sequences, checkpointing, the optimizer epoch. Product code, not proposable |
| 47 | `ggml/src/ggml.c` | new ops, and the backward graph builder |
| 32 | `ggml-cpu/ops.cpp` | mostly the gated-delta-net and flash-attention backward rewrites, which cannot move |
| 31 | `src/llama-graph.cpp` | differentiable KV cache, target log-probs, packed sequences |
| 30 | `ggml-cuda/ggml-cuda.cu` | per-op dispatch and `supports_op`; the kernels are out already |
| 28 | `ggml-metal/ggml-metal-ops.cpp` | per-op encoders; the kernels are out already |

## Syncing with upstream

```sh
git fetch upstream
git rebase --autosquash upstream/master
```

`git config rerere.enabled true` is worth it here: the same conflicts recur
sync after sync, and rerere replays the resolutions. A conflict in a generated
file is never resolved by hand: take either side, regenerate with `sync-fork`,
and fold the result into the RIR commits. The build and test steps that follow
a sync are in `docs/engineering/LLAMA_CPP_FORK_WORKFLOW.md` in the Retrograd
repository.
