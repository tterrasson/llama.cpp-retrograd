# The Retroback fork of llama.cpp

This branch (`retroback/main` on `tterrasson/llama.cpp-retroback`) carries the
changes Retroback needs to *train* a model with llama.cpp: backward passes for
ops that only had a forward, three backends brought up to the same contract,
memory-efficient training machinery, and the RIR generated-kernel integration.

It is a long-lived patch series rebased onto `upstream/master`, never merged.
Everything below exists so that the series stays readable, rebasable, and
partly proposable upstream.

## Seeing the delta

```sh
git diff upstream/master...HEAD          # the whole delta
git log --oneline upstream/master..HEAD  # one commit per patch family
```

The second one is the important command. Each commit is
`retro(<family>): <what> [n/N]`, where `<family>` is a key in
`crates/retroback-ffi/runtime/llama.cpp.lock`'s `[upstream_status]` section in
the Retroback repository. That file records, for every family, whether it
belongs upstream and why. The history and the lockfile are meant to agree:
a family in one and not the other is a bug in the bookkeeping.

To extract one family:

```sh
git log --oneline --grep 'retro(metal_reduction_ops)' upstream/master..HEAD
```

`[n/N]` means the family was written in several sittings and never
re-ordered. The parts are contiguous in time, not adjacent in the log.

## Invariants

These are what keep a rebase onto a moving upstream cheap. Breaking one is
always possible, but it should be a decision, not an accident.

1. **Never delete an upstream file.** A deleted file that upstream keeps
   editing is a delete/modify conflict on every sync, forever. The fork once
   deleted all of `.github/` (69 files) and paid that price; the files are back
   and GitHub Actions is turned off in the fork's repository settings instead.
   `AGENTS.md` is the one exception — it is fork-owned on purpose, and it is a
   *modification*, not a deletion.

2. **Additive code goes in a fork-owned file.** A new kernel, a new helper, a
   new translation unit — anything that is purely an addition — belongs in a
   file upstream has never heard of, reached from upstream's dispatcher by one
   line. The existing homes:

   | Backend | Fork-owned file | What goes in it |
   |---|---|---|
   | CPU | `ggml/src/ggml-cpu/retro-ops.cpp` | compute kernels the fork adds |
   | CPU | `ggml/src/ggml-cpu/retro-ops.h` | the few symbols `ops.cpp` calls back into |
   | Metal | `ggml/src/ggml-metal/kernels/retro.metal` | hand-written Metal kernels |
   | Metal | `ggml/src/ggml-metal/kernels/rir.metal` | generated RIR kernels |
   | Vulkan | `ggml/src/ggml-vulkan/ggml-vulkan-rir.cpp` | RIR SPIR-V blob lookup |
   | Vulkan | `vulkan-shaders/rir_*.comp` | generated RIR shaders |
   | CUDA | `ggml/src/ggml-cuda/{flash-attn-back,ssm-back,fused-sparse-ce,gated-delta-net-back,conv_rs_gather}.cu` | training kernels |
   | shared | `ggml/src/ggml-retro-quant.h` | the dequant type table (generated by `rir-gen`) |
   | shared | `ggml/src/ggml-rir/` | the RIR registry, contract and dispatch |

   The two `.metal` files are per-op kernel libraries, one compiled Metal
   library each, since upstream split the monolithic `ggml-metal.metal`
   (`b615f5b4b`). Each one has to be listed **twice**: in
   `METALLIB_KERNEL_SOURCES` (`ggml-metal/CMakeLists.txt`), which compiles and
   embeds it, and in `GGML_METAL_LIBS` (`ggml-metal-device.m`), which is what
   the runtime searches. A file present in the first list only is compiled,
   embedded, and never found — `ggml_metal_library_compile_pipeline` reports
   `kernel not found in any metal library` and the caller dereferences a null
   pipeline.

3. **Rewrites of upstream functions stay in place.** Where the fork changes how
   an existing function behaves — `ggml_compute_forward_gated_delta_net`,
   `ggml_compute_forward_flash_attn_back_f32` — there is no seam to cut along,
   and pretending otherwise would just fork the function under another name.
   Those stay in upstream's file and show up as conflicts on rebase. That is
   correct: they *are* changes to upstream code.

4. **Every hunk in an upstream file says why.** The convention is a
   `// retro delta:` comment. It is what tells the next rebase whether a
   conflict should be resolved toward upstream or toward the fork.

5. **A new `GGML_OP` is expensive and that is nobody's fault.** Registering one
   means touching `ggml.h`, `ggml.c`, `ggml-alloc.c` and every backend's
   `supports_op` and compute switch. There is no way to make that additive.
   Weigh it before adding an op.

## Where the fork touches upstream files

The point of the table is that it should shrink. Regenerate it with:

```sh
for f in $(git diff --name-only --diff-filter=M upstream/master...HEAD); do
  printf '%3d  %s\n' "$(git diff -U0 upstream/master...HEAD -- "$f" | grep -c '^@@')" "$f"
done | sort -rn
```

The heavy ones, and why:

| Hunks | File | Why it is hard to shrink |
|---:|---|---|
| 87 | `ggml-vulkan/ggml-vulkan.cpp` | one 20 000-line unit holds pipelines, `supports_op` and every op's encoder; the RIR chain is already one function (`ggml_vk_rir_try`), the rest is per-op registration |
| 52 | `src/llama-context.cpp` | the training loop itself — packed sequences, checkpointing, the optimizer epoch. Product code, not proposable |
| 41 | `ggml/src/ggml.c` | new ops, and the backward graph builder |
| 35 | `ggml/src/ggml-opt.cpp` | the optimizer control surface (clipping, state access, scratch reuse) |
| 28 | `ggml-metal/ggml-metal-ops.cpp` | per-op encoders; the kernels themselves are out already |
| 27 | `ggml-cpu/ops.cpp` | 1090 of its 1423 added lines are the gated-delta-net backward rewrite, which cannot move |

## Rebasing

See `docs/LLAMA_CPP_UPSTREAM_REBASE.md` in the Retroback repository.
`git config rerere.enabled true` is worth it here: the same conflicts recur
sync after sync, and rerere replays the resolutions.
